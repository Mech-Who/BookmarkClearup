# BookmarkClearup 项目现状与后续开发计划

> 整理日期：2026-09-02  
> 当前版本：`0.1.0`  
> 计划状态：初版，后续应随开发进展持续更新

## 1. 项目概览

BookmarkClearup 是一个面向 Windows 的 Python 本地工具，用于读取 Chrome 和 Edge 默认用户配置中的 `Bookmarks` JSON 文件，合并两套书签，并将结果回写到 Chrome。

项目目前已具备核心概念验证能力：能够把浏览器书签解析为目录树，按 URL 去重，将新增书签插入对应路径，回写前为目标文件生成 `.bak` 备份。

当前实现更接近开发者脚本，还不适合直接作为稳定工具发布。主要原因是测试无法正常收集、入口会直接修改真实书签文件、异常输入保护不足，并且缺少预览、确认和可靠恢复机制。

## 2. 当前技术与目录结构

| 位置 | 当前职责 |
| --- | --- |
| `main.py` | 配置日志，读取 Chrome 和 Edge 默认书签文件，执行合并并覆盖 Chrome 文件 |
| `src/constant.py` | 根据 Windows 环境变量提供 Chrome、Edge 默认书签路径 |
| `src/entity.py` | 定义书签、目录、组合树和迭代器，并暴露 JSON/HTML 导入导出接口 |
| `src/functional.py` | 实现 JSON 递归解析、URL 去重、路径插入、树合并、序列化和遍历 |
| `src/metaclasses.py` | 提供日志元类和计时元类，目前计时能力未进入业务链路 |
| `test/` | 保存解析、导出和合并的脚本式测试，当前不能作为可靠的自动化测试运行 |
| `asset/` | 保存项目结构图 |
| `pyproject.toml` | 声明 Python 3.11+、项目元数据和运行依赖 |

当前运行链路如下：

```text
main
  -> 读取 Chrome / Edge Bookmarks JSON
  -> 解析 roots.bookmark_bar
  -> 构建 BookmarkFolder / BookmarkPage 组合树
  -> 遍历页面并按 URL 去重
  -> 按来源路径创建目录、插入新增书签
  -> 将组合树序列化为 JSON
  -> 备份 Chrome Bookmarks 为 .bak
  -> 覆盖 Chrome 的 roots.bookmark_bar 并写回文件
```

项目使用 `uv` 管理环境，要求 Python 3.11 及以上。当前依赖为 `lxml` 和 `requests`，其中 `requests` 暂未发现实际使用点。

## 3. 已有能力与范围边界

### 3.1 已实现

- 读取 Chrome、Edge 本地 JSON 书签文件。
- 将书签和目录解析为带父子关系及路径信息的组合树。
- 合并两个或多个书签树，并按 URL 判断重复页面。
- 根据来源路径寻找或创建目标目录。
- 将合并结果序列化回浏览器 JSON 结构。
- 覆盖目标文件前生成 `.bak` 备份。
- 提供初步的 HTML 解析入口。

### 3.2 尚未完成

- HTML 书签的保真导入与导出。
- macOS、Linux 路径支持。
- Chrome、Edge 之外的浏览器及多 Profile 支持。
- 可配置的重复判定和冲突处理策略。
- 面向用户的命令行参数、预览模式和明确确认。
- 可重复运行的自动化测试、持续集成和发布流程。
- 基于真实数据规模的性能基准与针对性优化。

## 4. 当前工程状态

### 4.1 已验证结果

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| Git 工作区 | 通过 | `main` 与 `origin/main` 一致，无未提交修改 |
| Python 编译检查 | 通过 | `uv run python -m compileall -q src main.py test` 成功 |
| 默认 pytest | 失败 | 项目没有声明或安装 `pytest` |
| 临时安装 pytest 后收集 | 失败 | 直接调用 pytest 时无法导入 `src` |
| `python -m pytest` 收集 | 失败 | `functional.py` 的 `Generator` 注解参数不足，在导入时触发 `TypeError` |
| CI 与质量工具 | 缺失 | 未发现 CI、ruff/mypy/coverage、pre-commit 等项目配置 |

因此，当前不能用自动化测试证明合并结果和文件回写行为正确。恢复测试收集必须是后续开发的第一项工作。

### 4.2 关键风险

| 优先级 | 风险 | 影响 |
| --- | --- | --- |
| P0 | 类型注解在模块导入时触发异常 | 测试无法收集，核心模块不能稳定导入 |
| P0 | 测试是顶层执行脚本，部分依赖本机 Chrome 文件 | 测试不可重复，无法接入 CI |
| P1 | 程序默认直接覆盖真实 Chrome 书签文件 | 错误合并可能造成用户数据损失 |
| P1 | 写回不是临时文件加原子替换，固定 `.bak` 会被覆盖 | 中断或多次运行后恢复能力不足 |
| P1 | 默认参数包含预先计算的时间、UUID 和可变对象 | 不同实例可能共享意外状态或元数据 |
| P1 | 部分异常只构造但未 `raise`，空合并和迭代结束等边界未正确处理 | 错误可能被静默掩盖或以非预期异常暴露 |
| P1 | 只处理 `roots.bookmark_bar` | `other`、`synced` 等根节点不会参与合并 |
| P1 | 合并会原地修改第一个书签树，新增顺序可能不稳定 | 调用方难以预测副作用，输出难以复现 |
| P2 | HTML 实现不完整，页面构造方式疑似不匹配 | HTML 路线当前不可用，且可能丢目录及元数据 |
| P2 | 默认路径仅支持 Windows 默认 Profile | 适用用户和使用场景受限 |

## 5. 后续开发目标与原则

后续开发的首要目标不是增加格式或浏览器数量，而是把现有 JSON 合并能力变成可验证、可预览、可恢复的稳定工具。

开发遵循以下原则：

1. 先保证数据正确性和可恢复性，再扩展功能与性能。
2. 解析、合并、序列化采用纯内存逻辑，文件读写集中在独立边界。
3. 默认不覆盖真实文件；覆盖行为必须由用户显式选择。
4. 所有缺陷修复和新能力先补测试，再修改实现。
5. 保留浏览器 JSON 中本项目不理解的字段，避免无意破坏浏览器数据。
6. 性能优化以基准数据为依据，不提前增加结构复杂度。

## 6. 分阶段开发路线

### 阶段 0：恢复可测试性（P0，预计 0.5～1 天）

目标：让项目在干净环境中可安装、可导入、可执行测试。

- [ ] 修复 `Generator` 类型注解，避免导入阶段异常。
- [ ] 明确包结构和测试导入方式，消除“把测试拖到根目录”的要求。
- [ ] 将 `pytest` 声明为开发依赖，并记录唯一测试命令。
- [ ] 把三个顶层执行测试改为标准 pytest 测试函数。
- [ ] 使用仓库内固定夹具替代真实浏览器书签文件。
- [ ] 建立最小测试基线并记录当前预期行为。

验收标准：全新检出后可通过一条 `uv` 命令运行测试；测试收集成功；测试过程不读取或修改用户浏览器目录。

### 阶段 1：修复核心正确性（P0/P1，预计 1～2 天）

目标：让解析、合并和序列化逻辑在内存中具备明确、稳定的契约。

- [ ] 修复时间、UUID、列表和字典等不安全默认参数。
- [ ] 修复传入 ID 被忽略、未知节点类型未抛异常等确定性缺陷。
- [ ] 让迭代器以 `StopIteration` 正常结束。
- [ ] 为 `merge()` 的空输入、单输入和多输入定义行为。
- [ ] 明确页面等价规则，默认按规范化 URL 去重，并保证非同类型比较安全。
- [ ] 明确合并是否允许修改输入对象；优先返回独立结果，避免隐式副作用。
- [ ] 保证输出顺序稳定，避免集合迭代导致同一输入产生不同结果。
- [ ] 为缺字段、未知类型、空目录、重复 URL、同名目录等场景补充测试。

验收标准：核心逻辑不依赖本机文件；边界场景均有断言；相同输入重复运行得到相同输出；失败时抛出可理解的领域异常。

### 阶段 2：安全文件读写与 CLI（P1，预计 2～4 天）

目标：把脚本改造成默认安全、操作意图清晰的命令行工具。

- [ ] 分离“读取/写入文件”和“解析/合并数据”两层职责。
- [ ] 增加 CLI 参数：输入文件、基准文件、输出文件、合并策略和日志级别。
- [ ] 默认使用 `--dry-run` 或输出到新文件，只展示统计结果，不覆盖源文件。
- [ ] 覆盖真实书签文件前要求显式参数，并输出将要修改的准确路径。
- [ ] 使用临时文件写入、内容校验和同卷原子替换。
- [ ] 将备份改为带时间戳或版本号的文件，并提供恢复命令或清晰恢复说明。
- [ ] 自动创建日志目录，统一 `print` 与日志行为，避免库函数产生控制台副作用。
- [ ] 对文件不存在、权限不足、JSON 损坏、浏览器占用和磁盘写入失败提供明确错误。
- [ ] 补充 dry-run、备份、原子替换及失败回滚的端到端测试。

验收标准：默认命令不修改源文件；显式覆盖时始终产生可识别备份；模拟写入失败后原文件保持完整；CLI 返回码可被脚本和 CI 判断。

### 阶段 3：完善浏览器 JSON 支持（P1，预计 2～3 天）

目标：完整处理主流 Chromium 书签根节点和用户常见配置。

- [ ] 支持 `bookmark_bar`、`other`、`synced` 等已存在根节点。
- [ ] 保留校验和及未知顶层字段，明确哪些字段由浏览器重新生成。
- [ ] 支持指定 Profile，并检测常见 Chrome、Edge 配置目录。
- [ ] 抽象浏览器适配层，为 Chromium 系浏览器复用解析能力。
- [ ] 为根节点缺失、多 Profile、不同浏览器字段差异补测试夹具。
- [ ] 验证回写后 Chrome、Edge 能正常打开、同步和再次保存书签。

验收标准：支持指定浏览器和 Profile；不会丢失未参与合并的根节点；至少用两组脱敏真实样本完成往返验证。

### 阶段 4：HTML 与跨平台扩展（P2，预计 3～6 天）

目标：提供比直接修改浏览器配置更通用的导入导出路径。

- [ ] 先定义 Netscape Bookmark HTML 的领域映射和保真范围。
- [ ] 修复 HTML 页面对象构造问题，保留目录层级、标题、URL 和时间元数据。
- [ ] 实现 HTML 导出，并补充 HTML 导入到导出的往返测试。
- [ ] 将默认路径检测扩展到 macOS 和 Linux，同时保留显式路径覆盖能力。
- [ ] 评估 Firefox 等非 Chromium 浏览器；只有格式契约明确后再增加适配器。

验收标准：HTML 导入导出不丢目录层级；跨平台逻辑有平台独立单元测试；没有受支持浏览器时仍可通过显式文件路径运行。

### 阶段 5：工程化与发布（P2，预计 1～2 天）

目标：建立可持续维护和发布的最低工程基线。

- [ ] 补全 `pyproject.toml` 的描述、CLI 入口和开发依赖。
- [ ] 移除未使用依赖，或为其补充明确用途。
- [ ] 配置格式检查、静态检查、测试和覆盖率。
- [ ] 增加 CI，在受支持的 Python 版本上运行检查。
- [ ] 更新 README，补充安装、dry-run、安全覆盖、恢复和故障排查说明。
- [ ] 定义版本号、变更记录和首个可发布版本的完成标准。

验收标准：提交可以在 CI 中自动验证；用户无需阅读源码即可完成安装、预览、合并和恢复；项目可构建并安装 CLI。

### 阶段 6：性能优化（P3，按数据决定）

目标：只针对可复现的性能瓶颈进行优化。

- [ ] 建立不同规模书签树的解析、合并和序列化基准。
- [ ] 记录 CPU、内存和输出稳定性指标。
- [ ] 评估以 URL 和目录路径索引替代重复递归查找。
- [ ] 对比树式合并与当前“过滤后插入”方案的复杂度和可维护性。

验收标准：每项优化都有优化前后数据；正确性测试保持通过；不为了小规模数据的微小收益增加明显维护成本。

## 7. 建议的首个迭代

首个迭代只覆盖阶段 0 和阶段 1，不同时开发 HTML、跨平台或新浏览器功能。

建议交付顺序：

1. 修复模块导入错误并建立 pytest 配置。
2. 建立最小、完整和异常三类 JSON 测试夹具。
3. 把现有脚本式测试迁移为无本机依赖的断言测试。
4. 修复默认参数、异常抛出、ID、迭代器和空合并问题。
5. 固化当前 URL 去重和路径插入行为。
6. 明确并实现稳定输出与输入对象副作用策略。
7. 更新本文档的完成状态，记录遗留决策。

本迭代完成后，项目应从“能运行的脚本”进入“核心行为可验证的工具库”阶段，为安全 CLI 和文件写回改造提供稳定基础。

## 8. 需要提前确认的产品决策

以下决策会直接影响数据模型和合并规则，应在阶段 1 或阶段 2 开始前确定：

- 同一 URL 出现在不同目录时，是只保留一份，还是允许按目录保留多份？
- 同一 URL 标题不同或元数据不同时，以基准文件、较新记录还是用户选择为准？
- 合并是单向追加到基准文件，还是生成两个浏览器都可采用的独立结果？
- 默认操作是否必须是 dry-run，以及覆盖真实文件需要哪种显式确认？
- 备份保留数量、命名方式和自动清理策略是什么？
- 首个正式版本优先支持 JSON 安全合并，还是必须同时包含 HTML 工作流？

在这些问题明确前，开发可以继续完成测试基础和无争议缺陷修复，但不应固化冲突合并与覆盖策略。

## 9. 文档归档约定

从本计划开始，项目文档统一保存在仓库根目录的 `doc/` 下。

- 人工编写、评审确认或需要长期维护的正式文档放在 `doc/` 对应主题目录。
- AI 生成的分析、计划、阶段总结和草稿统一放在 `doc/ai/`。
- AI 文档确认转为正式规范后，应迁移到 `doc/` 的正式位置，并标记来源、确认日期和维护人。
- 文档中的计划项应随开发进展更新，不应只追加新计划而保留失效状态。
- 涉及用户数据安全、格式契约和合并规则的决策应形成独立 ADR 或设计说明。

建议后续文档结构：

```text
doc/
  architecture/       # 架构和模块边界
  decisions/          # ADR 与关键产品/技术决策
  guides/             # 安装、使用、恢复和故障排查
  ai/                 # AI 生成的分析、计划和草稿
```

## 10. 计划维护方式

每完成一个阶段，应更新任务勾选状态、实际完成时间、偏差原因和新增风险。若实现方案改变了数据格式或命令行契约，应先更新相应设计文档，再更新本计划的依赖关系。

建议以“测试通过、行为可验证、用户数据可恢复”作为阶段关闭条件，而不是仅以代码已经提交作为完成标准。
